# Gvboard 部署与迁移文档

本文档说明全新安装、Docker 部署、接入原 v2board 生产库、MySQL → PostgreSQL 转换、分离部署、主题安装、多实例、升级与备份；使用宝塔面板的用户可直接看第 13 节。插件的安装与开发见 `docs/插件开发说明.md`。

## 1. 环境要求

| 组件 | 版本 |
|------|------|
| 数据库 | MySQL 5.7+ / 8.0（或兼容的 MariaDB）；或 PostgreSQL 13+ |
| Redis | 6.0+（缓存、队列、会话、定时任务锁） |
| 反向代理 | Nginx 等（HTTPS、获取真实 IP） |
| 构建（自行编译时） | Go 1.26（使用最新补丁版本）、Node.js 20+（只有修改前端时需要） |

Gvboard 是单个可执行文件，用户端、管理端页面已编译在程序中，不需要 PHP、Web 根目录或额外的前端文件。

用户量较大（数十万以上）时，MySQL 的 `innodb_buffer_pool_size` 应能放下用户表与订阅表（100 万用户约 1 GB）。默认的 128 MB 放不下时，节点拉取用户列表要频繁读磁盘，会慢数倍。

## 2. 命令行速查

| 命令 | 说明 |
|------|------|
| `gvboard init [--app-key ...] [--api-prefix ...] [--mode all\|api] [--db mysql\|postgres] [--migrated]` | 生成配置文件（随机生成 API 前缀与签名密钥） |
| `gvboard init ... [--listen 127.0.0.1:8080] [--db-host ...] [--db-port ...] [--db-name ...] [--db-user ...] [--redis-addr ...] [--redis-db ...]` | 生成配置时直接写入监听地址与连接信息；密码不提供命令行参数（会留在命令历史中），通过环境变量 `GVB_DATABASE_PASSWORD`、`GVB_REDIS_PASSWORD` 传入 |
| `gvboard migrate [--status]` | 创建 / 升级表结构、执行一次性数据迁移，补齐管理端路径与订阅路径；可重复执行 |
| `gvboard import-config -f v2board.php [--dry-run]` | 导入原项目 `config/v2board.php` 中的系统设置 |
| `gvboard create-admin <邮箱>` | 创建管理员（邮箱未注册时创建账号并显示随机密码）或把已有账号设为管理员，并显示管理端地址 |
| `gvboard reset-password <邮箱>` | 把用户密码重置为随机密码，并注销其全部登录会话 |
| `gvboard serve` | 启动服务（按配置同时运行队列处理与定时任务） |
| `gvboard db-convert --to postgres://... [--skip-logs]` | MySQL 全量复制到 PostgreSQL 空库 |
| `gvboard job list` / `gvboard job run <任务名>` | 查看 / 立即执行定时任务（管理端“系统状态”页面也可执行） |
| `gvboard check-server` | 立即检查掉线节点并通知管理员 |
| `gvboard clear-user` | 删除没有任何数据的用户（从未登录、没有套餐 / 流量 / 订单 / 余额 / 佣金） |
| `gvboard reset-user` | 重置所有订阅的 uuid 与 token（所有订阅链接失效，慎用） |
| `gvboard version` | 版本 |

所有命令默认读取当前目录的 `config.yaml`，可用 `-c 路径` 指定。

## 3. 配置文件

`gvboard init` 生成的 `config.yaml` 中每一项都有中文注释。常用项：

| 配置 | 说明 |
|------|------|
| `app.key` | 签名密钥。接入原生产库时必须填原项目 `.env` 中的 `APP_KEY`（含 `base64:` 前缀），否则 Shadowsocks 2022 节点的密钥会变化 |
| `app.timezone` | 业务时区（流量重置、统计、提醒按此时区计算） |
| `server.mode` | `all` 不分离部署；`api` 分离部署（只提供 API） |
| `server.trusted_proxies` | 反向代理地址（支持 CIDR），只有来自这些地址的 `X-Forwarded-For` / `X-Real-IP` 才会被采信 |
| `server.theme_dir` | 外部主题目录（默认 `themes`） |
| `api.prefix` | 原生 API 前缀（随机生成）。修改后分离部署的前端 `config.js` 需同步，已发起但未回调的支付订单会回调失败 |
| `database.*` / `redis.*` | 连接信息 |
| `cors.allow_origins` | 分离部署时的前端域名 |
| `compat.v2board_api` | 原 `/api/v1` 兼容层（默认关闭，开启会暴露原项目特征，仅供旧客户端过渡） |
| `compat.legacy_subscribe` | 原订阅路径 `/api/v1/client/subscribe`（迁移站点建议开启，老订阅链接可继续使用） |
| `compat.legacy_callback` | 原支付回调与 Telegram Webhook 路径（迁移过渡期使用） |
| `worker.enabled` / `scheduler.enabled` | 本实例是否处理队列 / 执行定时任务（多实例时见第 9 节） |
| `geoip.*` | ip2region 离线库路径（Telegram 工单提醒显示用户位置，可不填） |

所有配置项都可用环境变量覆盖：`GVB_` + 大写路径（点换成下划线），例如 `GVB_DATABASE_PASSWORD`；列表用英文逗号分隔，例如 `GVB_SERVER_TRUSTED_PROXIES=127.0.0.1,172.16.0.0/12`。

业务设置（站点名称、邮件、支付、节点通信密钥等）存数据库，在管理端“系统配置”中修改，多实例自动同步。

### 3.1 使用 CDN 或多层代理时获取真实 IP

Gvboard 从 `X-Forwarded-For` 右侧向左跳过可信代理，取第一个不可信的地址作为用户 IP。前面还有 CDN 时，必须把 CDN 的回源 IP 段也加入可信代理，否则所有用户都会被记成 CDN 节点的 IP，IP 注册限制、IP 登录限制、订阅风控和日志都会失效或误伤。

- 在管理端“系统配置 → 安全 → 可信代理IP段”中填写 CDN 的回源 IP 段（各 CDN 服务商的文档中有列表，变更时需同步更新），保存后立即生效，与 `server.trusted_proxies` 合并。不能填写 `0.0.0.0/0` 等过大的范围（IPv4 大于 /8、IPv6 大于 /16 会被拒绝），否则任何人都能伪造 IP。
- Nginx 需用 `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` 保留 CDN 传来的转发链（`deploy/nginx` 中的示例和宝塔默认配置都是这样），不要改成 `$remote_addr`。
- 管理端仪表盘会统计最近的请求：如果较多请求（不少于 20 个且占 30% 以上）前面还有一层未被信任的代理，会提示“可能没有正确识别用户真实 IP”，并列出被当作用户 IP 的地址示例。

## 4. 全新安装（二进制）

### 4.1 使用安装脚本（推荐）

发布页（GitHub Releases）中的 `install.sh` 是交互式脚本，支持全新安装、从原 v2board 迁移、升级。以 root 用户执行：

```bash
mkdir -p /root/gvboard-install && cd /root/gvboard-install
curl -fsSLO https://github.com/<仓库>/releases/latest/download/install.sh
bash install.sh            # 显示菜单；也可直接 bash install.sh install / migrate / upgrade
```

全新安装的流程：

1. 自己先创建一个空数据库（MySQL 字符集 `utf8mb4`），准备好 Redis。
2. 脚本下载程序（校验 sha256），询问安装目录（宝塔默认 `/www/gvboard`，其它系统 `/opt/gvboard`）。
3. 输入数据库类型、地址、端口、库名、用户名、密码，脚本据此生成 `config.yaml`（权限 600）。
4. 脚本暂停，提示你打开 `config.yaml` 检查和修改配置项（监听端口、Redis 地址 / 密码 / 库号等），改完按回车继续。
5. 脚本检查数据库连接（失败时提示修改配置后重试），建表，询问管理员邮箱并创建管理员（显示随机密码与管理端地址）。
6. 最后显示进程守护（宝塔进程守护管理器或 systemd）与网站反向代理需要填写的内容，**由你自己配置**，脚本不改动系统服务和 Nginx。

| 环境变量（可选） | 说明 |
|------|------|
| `GITHUB_PROXY` | 国内服务器下载 GitHub 慢时使用的加速前缀，例如 `GITHUB_PROXY=https://ghfast.top/ bash install.sh` |
| `GVB_VERSION` | 安装指定版本，例如 `v1.0.0`，默认最新版本 |
| `GVB_BINARY` | 使用本地的 `gvboard` 可执行文件，不下载（也可直接把 `gvboard` 放在 `install.sh` 同一目录） |
| `GVB_REPO` | 下载仓库 `owner/name`（发布页中的脚本已自动填写，只有使用源码中的 `deploy/install.sh` 时需要） |

数据库密码输入时不回显，并通过环境变量传给 `gvboard init`，不会出现在命令历史与进程列表中。已有 `config.yaml` 时（例如重新运行脚本），脚本会询问保留还是重新生成（原文件备份为 `config.yaml.bak`）。

### 4.2 手动安装

```bash
# 1. 编译（或使用发布的可执行文件）
go build -trimpath -ldflags "-s -w" -o gvboard ./cmd/gvboard

# 2. 放到独立目录，生成配置
mkdir -p /opt/gvboard && cp gvboard /opt/gvboard/ && cd /opt/gvboard
./gvboard init                 # 分离部署加 --mode api，使用 PostgreSQL 加 --db postgres
vi config.yaml                 # 填写 database、redis

# 3. 建表、创建管理员
./gvboard migrate              # 输出中有管理端路径
./gvboard create-admin admin@example.com   # 显示随机密码（只显示一次）与管理端地址

# 4. 启动
./gvboard serve
```

登录管理端（`https://域名/{安全路径}/`）后先在“系统配置”中填写站点地址 `app_url`、节点通信密钥 `server_token`、邮件等设置。

systemd 服务示例 `/etc/systemd/system/gvboard.service`：

```ini
[Unit]
Description=Gvboard
After=network.target mysql.service redis.service

[Service]
User=gvboard
WorkingDirectory=/opt/gvboard
ExecStart=/opt/gvboard/gvboard serve
Restart=always
RestartSec=3
LimitNOFILE=65535
# 内存上限（JS 插件的内存无法单独限制，超出时进程被终止并自动重启），按服务器内存调整
MemoryMax=2G

[Install]
WantedBy=multi-user.target
```

```bash
useradd -r -s /usr/sbin/nologin gvboard && chown -R gvboard /opt/gvboard && chmod 600 /opt/gvboard/config.yaml
systemctl daemon-reload && systemctl enable --now gvboard
```

Nginx 反向代理示例见 `deploy/nginx/embedded.conf`（Gvboard 与 Nginx 在同一台机器时，默认的 `trusted_proxies: ["127.0.0.1", "::1"]` 即可取得真实 IP）。

## 5. Docker 部署

`deploy/` 中提供 `docker-compose.yml`（Gvboard + MySQL 8.0 + Redis）：

```bash
cd deploy
cp .env.example .env                                  # 设置 DB_PASSWORD、DB_ROOT_PASSWORD、REDIS_PASSWORD
docker compose build                                  # 国内网络在 .env 中改 GOPROXY、NPM_REGISTRY
docker compose run --rm gvboard init                  # 配置写入数据卷 /app/data/config.yaml
docker compose run --rm gvboard migrate
docker compose run --rm gvboard create-admin admin@example.com
docker compose up -d
```

- 数据库、Redis 连接由 compose 中的环境变量覆盖，`config.yaml` 中只需保留生成的密钥与 API 前缀；修改其它配置：`docker compose run --rm --entrypoint vi gvboard config.yaml`，或用环境变量。
- Gvboard 端口只绑定 `127.0.0.1`（端口由 `.env` 的 `HTTP_PORT` 设置，默认 8080），由宿主机 Nginx 反向代理；compose 已把 Docker 网段 `172.16.0.0/12` 加入 `trusted_proxies`。
- 外部主题放在 `deploy/themes/<主题名>/`（只读挂载；目录不存在时 Docker 会自动创建空目录）。
- 新安装的原生 API 前缀为随机值（`config.yaml` 的 `api.prefix`），且默认不开启原 v2board 兼容接口（`compat.v2board_api: false`），因此 `/api/v1/...` 返回 404 属于正常现象（节点通信接口 `/api/v1/server/...`、`/api/v2/server/...` 不受此开关影响，始终可用，对接 v2node / V2bX 无需开启兼容开关）；`init --migrated` 只默认开启原订阅路径（`compat.legacy_subscribe`），其余兼容开关见第 6 节。
- 镜像以非 root 用户（UID 10001）运行，不包含构建工具；镜像构建时会重新编译前端并做去特征检查。
- 单独构建镜像：在项目根目录执行 `docker build -t gvboard:latest .`。

## 6. 接入原 v2board 生产库

Gvboard 直接使用原数据库（`v2_` 表名、字段保持原样），迁移为单向，**务必先备份**。

> **推荐使用迁移脚本**：把原站的数据库备份、`v2board.php`、`.env` 放进脚本目录下的一个文件夹，执行 `bash install.sh migrate` 并输入该文件夹路径，脚本自动导入数据库并完成 6.2 的命令，详细步骤见 13.7（不限于宝塔）。下面是手动操作说明，也可用来理解脚本做了什么。

### 6.1 迁移前准备

1. 记录原站信息：`.env` 中的 `APP_KEY`、数据库连接；`config/v2board.php`；`resources/rules/custom.*`（自定义订阅模板，如有）。
2. 停止原面板：Web 服务、队列（`php artisan horizon` 或 supervisor 中的进程）、计划任务（crontab 中的 `php artisan schedule:run`）。
3. 等待 1～2 分钟，让原面板把 Redis 中的流量写入数据库（原项目每分钟写一次）。
4. 备份数据库（以下命令只是示例，按实际修改）：

   ```bash
   mysqldump --single-transaction --routines --triggers --default-character-set=utf8mb4 -u root -p v2board > v2board-$(date +%F).sql
   ```

   同时保存原站目录（含 `.env`、`config/v2board.php`）。备份文件含全部用户数据，请妥善保管，不要上传到公开位置。

### 6.2 执行迁移

```bash
./gvboard init --app-key "base64:原APP_KEY" --migrated   # --migrated 开启旧订阅路径兼容
vi config.yaml                                          # database 填原数据库，redis 建议用新的库号或前缀
./gvboard migrate --status                              # 先查看将要执行的迁移步骤
./gvboard migrate
./gvboard import-config -f /原站目录/config/v2board.php --dry-run   # 预览
./gvboard import-config -f /原站目录/config/v2board.php
./gvboard create-admin 原管理员邮箱                        # 已有账号只会显示管理端地址，不改密码
./gvboard serve
```

`migrate` 会：补建 Gvboard 新增的表与列；为每个用户把原订阅复制为主订阅（订阅 ID = 用户 ID，`uuid`、`token` 不变）；历史订单、流量统计关联主订阅；删除 `v2_stat_user` 的原唯一索引；MySQL 下把仍为 utf8 的工单、公告表转为 utf8mb4。原有列与数据不会被修改或删除。

迁移会被以下情况中止（数据库不做修改），按提示处理后重新执行：

| 情况 | 处理 |
|------|------|
| 多个用户的 `uuid` 相同 | 在原面板为列出的用户重置订阅后再迁移 |
| 库中有 Xboard 创建的 `v2_settings` 表（带 `group` / `type` 列） | 按提示改名保留（`RENAME TABLE v2_settings TO v2_settings_xboard_bak`），设置用 `import-config` 导入 |
| PostgreSQL 下存在只有大小写不同的邮箱 | 合并或修改这些账号 |

### 6.3 迁移后需要注意

| 项目 | 说明 |
|------|------|
| 管理端地址 | 原项目允许 8 位路径，Gvboard 要求至少 16 位：原路径不满足时会重新生成，`migrate` / `import-config` / `create-admin` 都会显示新地址 |
| 登录状态 | 所有用户与管理员需要重新登录一次；订阅链接、节点不受影响 |
| 订阅链接 | 订阅 token 不变；原站设置了 `subscribe_path` 时原链接可直接使用，否则开启 `compat.legacy_subscribe`（`--migrated` 已开启）保证 `/api/v1/client/subscribe?token=` 可用 |
| 节点（V2bX / v2node） | 无需修改配置（节点接口路径、通信密钥、用户 ID 均不变）；如原站有节点 IP 白名单需求，可设置 `node.ip_whitelist` |
| 支付回调 | 按订单传递回调地址的网关（EPay 系列等）自动使用新地址；在支付平台后台固定配置 Webhook 的网关（Stripe、Coinbase、BTCPay 等）需改为管理端“支付方式”中显示的新地址，或临时开启 `compat.legacy_callback`；切换时尚未回调的订单可能回调失败，请在低峰期切换 |
| Telegram | 在管理端“系统配置 → Telegram”中重新设置 Webhook（或改用长轮询） |
| 自定义订阅模板 | 把原站 `resources/rules/custom.*` 的内容粘贴到管理端“系统配置 → 订阅模板” |
| 主题 | 原项目主题不能使用，使用内置默认主题或按 `docs/主题开发说明.md` 开发 |
| PaytaroQR | 加密货币支付页 `/paytaro-qr/pay.php` 需自行用 Web 服务器部署 |
| 原 `/api/v1` 接口 | 默认关闭；只在仍有旧客户端依赖时临时开启 `compat.v2board_api` |

### 6.4 验证清单

1. 原用户用原密码登录用户端，能看到原订阅（套餐、流量、到期时间正确）。
2. 原订阅链接可获取节点。
3. 节点后端日志无认证错误，几分钟后管理端“节点管理”显示在线、流量有增长。
4. 下一笔测试订单能支付并开通。
5. 管理端“系统状态”中定时任务、队列处理器为“运行中”。

如需放弃迁移，停止 Gvboard 后用 6.1 的备份恢复数据库，再启动原面板。

## 7. MySQL → PostgreSQL 转换

```bash
# 1. 停止 Gvboard（serve），确保源库已执行过 gvboard migrate
# 2. 新建空的 PostgreSQL 数据库
createdb -U postgres gvboard
# 3. 转换（读取 config.yaml 中的 MySQL 连接）；密码通过 PGPASSWORD 传入，避免留在命令历史与进程列表中
read -rs PGPASSWORD && export PGPASSWORD
./gvboard db-convert --to "postgres://postgres@127.0.0.1:5432/gvboard?sslmode=disable"
unset PGPASSWORD
# 4. 把 config.yaml 的 database 改为 PostgreSQL（driver: postgres、port: 5432 ...），检查后启动
./gvboard migrate
./gvboard serve
```

- 自动在目标库创建表结构；全部数据在一个事务中写入，同步自增序列并逐表核对行数；失败时目标库不留数据，处理后可直接重试。
- 源库在只读的一致性快照中读取。
- 源库中不属于 Gvboard 的表（如人工备份表）与多出的列（如 Xboard 遗留的 `ips`、`excludes`）不复制，结束时列出。
- `--skip-logs` 不复制系统日志、邮件日志、订阅请求日志（只建表），日志很多时可缩短时间。
- 实测：生产库副本（MySQL 5.7，36 张表约 52 万行）用时约 12 秒。
- Redis 不需要转换，继续使用原来的即可。

## 8. 分离部署

API 与前端使用不同域名（示例 `api.example.com`、`www.example.com`、`admin.example.com`）：

1. Gvboard：`gvboard init --mode api`，或把 `server.mode` 改为 `api`；`cors.allow_origins` 填两个前端地址。分离模式下 Gvboard 不提供任何页面，用户端通过 `{api}/site` 获取站点公开配置。
2. 用户端：把 `internal/theme/builtin/default/` 中除 `theme.json` 外的文件复制到用户端站点根目录，按 `deploy/web/config.user.example.js` 编写 `config.js`。
3. 管理端：把 `internal/web/admin/` 中的文件复制到管理端站点根目录，按 `deploy/web/config.admin.example.js` 编写 `config.js`（含安全路径，建议限制访问来源或加 HTTP 认证）。
4. Nginx 示例：`deploy/nginx/separated.conf`。
5. 管理端“系统配置”：`app_url` 填用户端地址（邮件、支付返回页使用）；订阅地址 `subscribe_url` 填 API 地址。

## 9. 多实例部署

- 所有实例使用同一个数据库与 Redis，`config.yaml` 中的 `app.key`、`api.prefix` 必须相同。
- `worker.enabled`：至少一个实例开启（处理邮件、订单开通、流量统计、Telegram 通知、插件事件）。
- `scheduler.enabled`：可以全部开启，同一任务在同一时刻只会执行一次（Redis 锁）。
- 系统设置、插件、主题配置修改后各实例自动同步；外部主题目录需在每个实例上放置相同的文件。

## 10. 主题安装

不分离部署时，把主题目录放到 `server.theme_dir`（默认程序工作目录下的 `themes/`），每个子目录一个主题，目录中必须有 `theme.json` 与 `index.html`，之后在管理端“主题”页面切换与配置。与内置主题同名的外部主题优先。开发方法见 `docs/主题开发说明.md`。

## 11. 升级

使用安装脚本：`bash install.sh upgrade`。输入安装目录后，脚本下载新版本并校验 → 旧程序保留为 `gvboard.bak` → 替换程序 → 执行 `gvboard migrate`（失败时自动恢复旧程序）→ 提示你在进程守护管理器（或 `systemctl restart gvboard`）中重启。升级前仍需自行备份数据库。

手动升级：

1. 备份数据库与 `config.yaml`。
2. 替换可执行文件（Docker：`docker compose build` 或拉取新镜像）。
3. 执行 `gvboard migrate`（Docker：`docker compose run --rm gvboard migrate`）。
4. 重启服务。

### 11.1 节点审计（可选）

管理端「审计规则」页面的规则只由开启了审计的节点执行。节点使用 [v2node gvboard 分支](https://github.com/gunzi-666/v2node/tree/gvboard)，在节点配置的 `Nodes` 中给需要审计的节点加上 `"AuditEnable": true` 后重启 v2node。未开启的节点与常规版本完全相同，不请求审计接口。节点按拉取间隔获取规则，按上报间隔上报命中记录；面板按「订阅 + 规则 + 节点 + 自然日」合并审计日志，管理端可展开查看各访问目标；审计日志默认保留 30 天（系统配置 `audit_log_retention_days`）。节点机模式下在「节点机」页面为节点开启审计，不需要修改配置文件。

### 11.2 节点机一次性接入（可选）

不想给每台服务器分发通讯密钥、编写配置文件时使用，只支持 v2node gvboard 版与 v2node 类型的节点：

1. 系统配置 →“节点”中开启“节点机一次性接入”，建议同时填写“节点对接 API 地址”（节点机访问面板的地址）。
2. 左侧“服务器 → 节点机”添加节点机，选择运行的节点、需要审计的节点与日志级别，复制生成的安装命令，在服务器上以 root 执行：

   ```bash
   wget -N https://raw.githubusercontent.com/gunzi-666/v2node/gvboard/script/install.sh && bash install.sh --panel https://面板地址 --code 接入码
   ```

   接入码 30 分钟内有效、只能使用一次。已安装 v2node 的服务器也可以执行 `v2node enroll --panel 面板地址 --code 接入码` 后 `v2node restart`。
3. 接入后凭据保存在 `/etc/v2node/machine.json`（存在时忽略 `config.json`）；运行哪些节点、审计、日志级别在面板修改，节点机按拉取间隔自动生效。
4. 吊销或删除节点机后，节点机连续 3 次被拒绝时停止全部节点；更换服务器或重装系统时在列表中“生成安装命令”重新接入（旧凭据同时失效）。存在已接入的节点机时不能关闭开关。

面板配置了 `node.ip_whitelist` 时，节点机接入与拉取配置同样受白名单限制。

## 12. 备份

| 内容 | 方式 |
|------|------|
| 数据库（必须） | MySQL：`mysqldump --single-transaction ...`；PostgreSQL：`pg_dump -Fc ...`。设置、插件、JS 插件安装包都在数据库中 |
| `config.yaml`（必须） | 包含 `app.key`（登录凭证签名密钥，丢失或更换后所有用户需重新登录）与 API 前缀（更换后需同步前端与支付平台回调地址） |
| 外部主题目录、Go 插件源码（如有） | 文件备份 |
| Redis | 一般不需要备份（会话丢失只需重新登录）。节点上报的流量先累计在 Redis 中、每分钟写入数据库，停止服务后尚未写入的部分保留在 Redis 中、下次启动后写入，因此迁移或重建 Redis 前请先停止服务并等待 1 分钟以上（或执行 `gvboard job run traffic_update`） |

## 13. 宝塔面板部署

以下以宝塔 Linux 面板 9.x、域名 `example.com`、程序目录 `/www/gvboard` 为例（不同版本的菜单文字可能略有差异）。Gvboard 不需要 PHP，也不需要“计划任务”和队列进程：定时任务与队列都在 `gvboard serve` 进程中运行。

> **推荐使用安装脚本**：装好 Nginx、MySQL、Redis（13.1）并创建数据库（13.2）后，在宝塔“终端”中执行 4.1 的命令，选择“全新安装”，按提示输入数据库信息、按提示修改 `config.yaml`，脚本完成 13.3 的全部操作（默认目录 `/www/gvboard`），最后显示 13.4 进程守护与 13.5 反向代理要填写的内容，照着在面板中添加即可。从原 v2board 迁移见 13.7。下面 13.3 是手动操作步骤。

### 13.1 安装软件

“软件商店”中安装：

| 软件 | 说明 |
|------|------|
| Nginx | 任意稳定版本 |
| MySQL | 5.7 或 8.0（想用 PostgreSQL 可安装“PostgreSQL 管理器”） |
| Redis | 6.0 以上；安装后在 Redis 的“设置 → 性能调整”中设置 `requirepass` 密码（建议） |
| 进程守护管理器 | 即 Supervisor，用来让 Gvboard 常驻运行、崩溃自动重启 |

PHP 不需要安装（如果服务器上还有原 v2board，见 13.7）。

### 13.2 创建数据库

“数据库 → MySQL → 添加数据库”：数据库名 `gvboard`、用户名 `gvboard`、密码随机生成，字符集选 `utf8mb4`，访问权限“本地服务器”。记下数据库名、用户名、密码。

### 13.3 上传程序并生成配置

1. 准备 Linux 可执行文件：使用发布的程序（服务器为 ARM 时选 arm64 版本），或自行编译（Windows PowerShell，在项目根目录）：

   ```powershell
   $env:GOOS = "linux"
   $env:GOARCH = "amd64"
   go build -trimpath -ldflags "-s -w" -o gvboard ./cmd/gvboard
   Remove-Item Env:GOOS
   Remove-Item Env:GOARCH
   ```

   用户端、管理端页面已编译在程序中，只需上传这一个文件。
2. “文件”中新建目录 `/www/gvboard`（**不要放在网站根目录 `/www/wwwroot/...` 下**，避免配置文件被直接下载），把 `gvboard` 上传进去。
3. 打开宝塔“终端”，执行：

   ```bash
   cd /www/gvboard
   chmod +x gvboard
   ./gvboard init
   ```

4. 在“文件”中双击编辑 `/www/gvboard/config.yaml`：

   ```yaml
   server:
     listen: "127.0.0.1:8080"   # 只监听本机，由 Nginx 对外提供服务；8080 被占用时换一个端口
   database:
     driver: "mysql"
     host: "127.0.0.1"
     port: 3306
     name: "gvboard"            # 13.2 中的数据库名
     user: "gvboard"
     password: "数据库密码"
   redis:
     addr: "127.0.0.1:6379"
     password: "Redis 密码"     # 未设置则留空
     db: 0
   ```

5. 建表并创建管理员：

   ```bash
   ./gvboard migrate                           # 输出中有管理端路径，请记下
   ./gvboard create-admin admin@example.com    # 显示随机密码（只显示一次）与管理端地址
   chown -R www:www /www/gvboard
   chmod 600 /www/gvboard/config.yaml
   ```

### 13.4 进程守护

“软件商店 → 进程守护管理器 → 设置 → 添加守护进程”：

| 项目 | 填写 |
|------|------|
| 名称 | `gvboard` |
| 启动用户 | `www` |
| 运行目录 | `/www/gvboard` |
| 启动命令 | `/www/gvboard/gvboard serve` |
| 进程数量 | 1 |

保存后状态应为“运行中”。如果启动失败，点击“日志”查看原因（常见：数据库密码错误、Redis 密码错误、端口被占用）。之后重启 Gvboard 都在这里操作。

> 也可以使用宝塔“网站 → Go 项目”运行（执行文件 `/www/gvboard/gvboard`、执行命令 `/www/gvboard/gvboard serve`、端口 8080、运行用户 www），它会同时创建网站和反向代理；两种方式选一种即可，不要同时运行。

### 13.5 创建网站与反向代理

1. “网站 → 添加站点”：域名填 `example.com`，PHP 版本选“纯静态”，不创建数据库与 FTP。
2. 站点“设置 → SSL → Let's Encrypt”申请证书，并开启“强制 HTTPS”。
3. 站点“设置 → 反向代理 → 添加反向代理”：目标 URL `http://127.0.0.1:8080`，发送域名 `$host`，**不要开启缓存**。宝塔生成的配置已包含 `X-Real-IP` 与 `X-Forwarded-For`，Gvboard 默认的 `trusted_proxies`（127.0.0.1）即可取得用户真实 IP。
4. 站点“伪静态”保持为空（如有 `location /` 规则会与反向代理冲突）。
5. 防火墙（宝塔“安全”与云服务器安全组）只放行 80、443，**不要放行 8080**。

访问 `https://example.com` 即为用户端，`https://example.com/{管理端路径}/` 为管理端。登录管理端后在“系统配置”中填写站点地址（`https://example.com`）、节点通信密钥、邮件等设置。

### 13.6 升级

1. 宝塔“数据库”中备份数据库，“文件”中下载备份 `config.yaml`。
2. 进程守护管理器中停止 `gvboard`。
3. 上传新的 `gvboard` 覆盖旧文件，在终端执行：

   ```bash
   cd /www/gvboard
   chmod +x gvboard
   ./gvboard migrate
   chown www:www gvboard
   ```

4. 进程守护管理器中启动 `gvboard`。

也可以在终端执行 `bash install.sh upgrade`（见第 11 节），完成后在进程守护管理器中重启 `gvboard`。

### 13.7 从原 v2board 迁移（迁移脚本）

脚本把原站的数据库备份导入一个新数据库，用原 `APP_KEY` 生成配置，再升级表结构、导入原站设置。新旧服务器可以是同一台，也可以不同。建议在低峰期操作。

**第一步：在原站准备文件**

1. 停止原面板，避免导出后又产生新数据：宝塔“进程守护管理器”中停止 v2board 的 horizon 进程；“计划任务”中停用 `php artisan schedule:run`；等待 1～2 分钟（让 Redis 中的流量写入数据库）。建议同时在“网站”中停用原站点。
2. 宝塔“数据库”中找到原库，点“备份”，下载得到的 `.zip` 文件（也可以用 mysqldump 导出的 `.sql` / `.sql.gz`）。
3. 下载原站目录（如 `/www/wwwroot/v2board`）中的 `.env` 与 `config/v2board.php`。

**第二步：在新服务器上放好文件、建空库**

1. 宝塔“数据库 → 添加数据库”：新建一个空库（字符集 `utf8mb4`），记下库名、用户名、密码。
2. 新建脚本目录并下载脚本（宝塔“终端”中执行）：

   ```bash
   mkdir -p /root/gvboard-install && cd /root/gvboard-install
   curl -fsSLO https://github.com/<仓库>/releases/latest/download/install.sh
   ```

3. 在 `/root/gvboard-install` 下新建文件夹 `v2board`，把第一步的三个文件上传进去：

   ```
   /root/gvboard-install/
   ├── install.sh
   └── v2board/
       ├── 数据库备份.zip
       ├── v2board.php
       └── .env
   ```

   （宝塔“文件”中默认不显示以 `.` 开头的文件，上传后看不到 `.env` 属正常，可在终端用 `ls -a v2board` 确认。）

**第三步：运行脚本**

```bash
cd /root/gvboard-install
bash install.sh migrate
```

服务器下载 GitHub 慢时改为 `GITHUB_PROXY=https://ghfast.top/ bash install.sh migrate`。

脚本依次询问并执行（方括号中是默认值，直接回车即可）：

| 脚本询问 / 执行 | 你需要做什么 |
|------|------|
| 迁移文件夹路径 | 回车（默认就是脚本目录下的 `v2board`）。脚本检查三个文件，从 `.env` 读取 `APP_KEY` |
| 下载程序、安装目录 | 回车（默认 `/www/gvboard`） |
| 新数据库的地址、端口、库名、用户名、密码 | 填第二步新建的空库 |
| 导入数据库备份 | 无需操作，脚本解压并导入（数据量大时需要几分钟）；库中已有数据表时会询问是否跳过导入 |
| 修改配置文件 | 打开 `/www/gvboard/config.yaml` 检查 Redis 地址 / 密码 / 库号、监听端口，保存后回车 |
| 检查数据库连接 | 失败时按提示修改配置后回车重试 |
| 升级表结构 | 确认（只新增表和列，不修改原数据） |
| 导入原站设置 | 查看预览后确认 |
| 原管理员邮箱 | 输入后脚本显示新的管理端地址，**请记下**（密码不变） |

**第四步：按脚本最后的提示自行配置**

1. 执行脚本显示的 `chown` 命令设置文件归属。
2. 宝塔“进程守护管理器 → 添加守护进程”：按脚本显示的名称、启动用户、运行目录、启动命令填写（同 13.4）。
3. 网站切换到 Gvboard：
   - 同一台服务器：打开原站点“设置”，先“启用”站点，“伪静态”清空，PHP 版本改为“纯静态”，“反向代理”添加 `http://127.0.0.1:8080`（发送域名 `$host`，不开缓存）。
   - 新服务器：按 13.5 新建站点与反向代理，再把域名解析改到新服务器。
   
   域名、SSL 证书、节点后端配置都不需要改，用户的订阅链接继续可用（用户需要重新登录一次）。

**第五步：检查**

对照 6.3、6.4：原用户能用原密码登录、原订阅链接能获取节点、几分钟后“节点管理”中节点在线。Stripe 等在支付平台固定填写回调地址的网关需改为管理端“支付配置”中显示的新地址；Telegram 机器人需在“系统配置 → Telegram”中重新设置 Webhook。确认无误后删除 `/root/gvboard-install/v2board` 文件夹（含全部用户数据与密钥）。

**需要回退时**

迁移没有修改原数据库（数据导入的是新库），回退只需：停止 Gvboard 守护进程 → 原站点删除反向代理、恢复 PHP 版本与伪静态（或把域名解析改回原服务器）→ 重新启动原 horizon 进程与计划任务。

> 不使用脚本时的手动步骤：按第一步准备并把备份导入新库（或直接使用原库）→ 按 13.3 上传程序并执行 `./gvboard init --app-key "base64:原APP_KEY" --migrated`，`config.yaml` 的 `database` 填该库 → 执行 6.2 中的命令 → 按第四步配置进程守护与网站。

### 13.8 常见问题

| 现象 | 处理 |
|------|------|
| 打开网站显示 502 | Gvboard 未运行或端口不一致：查看进程守护日志，确认反向代理目标端口与 `server.listen` 相同 |
| 页面能打开但样式、脚本 404 | 站点配置文件中有 `location ~ .*\.(js\|css)?$` 等静态文件规则拦截了请求：在“设置 → 配置文件”中删除这些规则，或确认反向代理使用 `location ^~ /` |
| 用户登录 IP、订阅请求日志中的 IP 全部是 127.0.0.1 | 反向代理未传递 `X-Real-IP` / `X-Forwarded-For`，或 Gvboard 与 Nginx 不在同一台机器（把 Nginx 地址加入 `server.trusted_proxies`） |
| 用户 IP 全部是少数几个 CDN 节点的 IP | 网站接入了 CDN 但 CDN 回源 IP 段不在可信代理中，见第 3.1 节 |
| `/api/v1/...` 返回 404 | 正常：新安装默认不开启原 v2board 兼容接口，见第 3 节 `compat.*`；节点通信接口 `/api/v1/server/...` 不受影响 |
| 上传 JS 插件失败（提示请求过大） | 检查 Nginx 的 `client_max_body_size`（宝塔默认 50 MB，一般无需修改） |
| 脚本提示“连接失败” | 按显示的错误信息修改 `config.yaml` 中的数据库地址、端口、库名、用户名、密码，保存后在脚本中回车重试 |
| 守护进程启动后立即退出 | 查看守护进程日志：Redis 地址或密码错误（宝塔 Redis 设置了密码时需填写 `redis.password`）、监听端口被占用、`config.yaml` 属主不是运行用户 |
| 迁移脚本提示没有 `.env` | 宝塔“文件”默认隐藏以 `.` 开头的文件，确认已上传：终端执行 `ls -a` 查看迁移文件夹 |
| 迁移脚本提示需要 unzip | 执行 `yum install -y unzip`（CentOS）或 `apt install -y unzip`（Debian / Ubuntu）后重新运行 |
| 脚本下载程序失败 | 设置 `GITHUB_PROXY` 加速前缀；或在本地下载 Release 中的 `gvboard_linux_amd64.tar.gz`，解压后把 `gvboard` 上传到 `install.sh` 同一目录再运行脚本 |

## 14. 发布版本（GitHub Actions）

仓库中的 `.github/workflows/release.yml` 在推送 `v` 开头的标签时自动构建并发布 GitHub Release：

```bash
git tag v1.0.0
git push origin v1.0.0
```

流程：

1. **测试**：启动 MySQL 8.0、PostgreSQL 16、Redis 7 服务，执行 `go vet` 与全部 `go test`（包含数据库集成测试）；测试不通过不会发布。
2. **构建前端**：`npm ci`、`npm run build`（含类型检查）、去特征检查。
3. **交叉编译**：`CGO_ENABLED=0`，写入版本号（标签名）与构建时间（`gvboard version` 可查看），产物：

   | 文件 | 平台 |
   |------|------|
   | `gvboard_linux_amd64.tar.gz` / `gvboard_linux_arm64.tar.gz` | Linux 服务器（安装脚本下载的就是这两个） |
   | `gvboard_windows_amd64.zip` | Windows（本地测试） |
   | `gvboard_darwin_amd64.tar.gz` / `gvboard_darwin_arm64.tar.gz` | macOS（本地测试） |
   | `install.sh` | 安装 / 迁移 / 升级脚本，已自动填写本仓库地址 |
   | `sha256sums.txt` | 校验和，安装脚本下载后自动校验 |

4. **发布**：自动生成更新说明（两个标签之间的提交与 PR）；标签中带 `-` 的（如 `v1.0.0-beta.1`）标记为预发布版本，`releases/latest` 不会指向预发布版本。

在 Actions 页面也可以手动运行（workflow_dispatch），只构建、不发布，产物在运行详情的 Artifacts 中下载，用于检查构建是否正常。仓库设置中 Actions 的 Workflow permissions 需允许读写（工作流已声明 `contents: write`，默认设置即可）。
