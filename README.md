# Gvboard

Gvboard 是用 Go 重写的代理服务面板，功能与原 v2board（wyx2685 分支）对齐，可以直接接入原项目的生产数据库继续使用。

- 单个可执行文件：用户端、管理端页面已编译在程序中，不需要 PHP 与 Web 根目录
- 数据库支持 MySQL 5.7+ / 8.0 与 PostgreSQL 13+，提供 MySQL → PostgreSQL 转换命令
- 兼容原项目：数据库、节点通信接口、订阅格式、支付回调；迁移后老订阅链接可继续使用

## 主要功能

- **单账号多订阅**：一个账号可购买多个套餐，每个订阅独立的流量、到期时间、订阅链接
- **订阅风控**：按 User-Agent、IP、请求头等规则拦截或记录订阅请求，频率限制、防分享，请求日志与按订阅统计
- **插件**：内置插件（Go，编译进程序）与 JS 插件（沙箱运行，需声明权限与可访问的域名），可监听订单、工单等事件
- **主题**：内置主题，支持安装外部主题
- **部署方式**：前后端不分离（一个程序提供全部页面）或分离部署（前端单独放在 CDN / 静态站点）
- **通知**：多个 SMTP 服务器（故障转移 / 轮询）、管理端可编辑的邮件模板；Telegram 机器人，管理员通知可发到话题群组（订单、工单、告警、每日统计）
- **管理端**：订单补单、订阅管理、节点与权限组、优惠券、礼品卡、公告、工单、知识库、队列监控、系统日志

## 与原版对比

### 功能与架构

| 项目 | 原版 v2board（wyx2685） | Gvboard |
|------|------|------|
| 运行环境 | PHP + Laravel 8，需 Nginx + PHP-FPM（或 Webman）、Horizon 队列进程、cron 定时任务 | 单个可执行文件，队列与定时任务内置 |
| 数据库 | MySQL | MySQL / PostgreSQL |
| 订阅 | 一个账号一个订阅 | 一个账号多个订阅，各自独立流量与到期 |
| 订阅防护 | 一次性 / 限时订阅链接 | 同样支持；另有规则拦截（UA、IP、请求头）、频率限制、防分享、请求日志与统计 |
| 插件 | 无 | Go 内置插件、JS 插件 |
| 部署方式 | 前端随程序部署 | 不分离（页面编译在程序中）或分离部署（提供前端单独部署的配置） |
| 邮件 | 单个 SMTP，模板需改文件 | 多个 SMTP（故障转移 / 轮询），模板在管理端编辑 |
| Telegram 管理员通知 | 私聊管理员 | 可发到话题群组，按订单 / 工单 / 告警 / 每日统计分话题 |
| 已取消订单收到付款回调 | 不处理，也不通知 | 不处理，通知管理员；管理端可补单 |
| 数据迁移 | — | 直接接入原生产库，`gvboard migrate` 升级结构，老订阅链接可继续使用 |

### 性能实测

测试环境：同一台机器，三种服务各自限制为 **2 个 CPU 核心、2 GB 内存**，连接同一个 MySQL 8.0 与 Redis 7；数据为 1 万个有效用户、30 个节点；压测工具 k6 运行在其它核心上。原版使用 PHP 8.2（开启 opcache 与 JIT），FPM 模式为 Nginx + 40 个固定进程，Webman 模式使用原版自带的 `webman.php` 启动。Gvboard 的数据库由同一份原版数据经 `gvboard migrate` 迁移而来。两边返回的内容一致（响应大小相差不到 1%）。

每项测试重复 3 轮取中位数，3 轮之间的波动在 ±6% 以内。

#### 1 万用户

每秒请求数（越高越好），每个接口持续压测 30 秒，全部请求均成功：

| 接口 | 并发 | 原版 FPM | 原版 Webman | Gvboard | 相比 FPM | 相比 Webman |
|------|------|------|------|------|------|------|
| 节点拉取用户列表 | 20 | 28.6 | 24.3 | **95.9** | 3.4 倍 | 3.9 倍 |
| 订阅生成（Clash） | 50 | 84.2 | 98.3 | **359.6** | 4.3 倍 | 3.7 倍 |
| 用户信息 | 100 | 274.9 | 1468.8 | **2942.1** | 10.7 倍 | 2.0 倍 |
| 节点上报流量（每次 100 个用户） | 50 | 162.0 | 565.0 | **1908.4** | 11.8 倍 | 3.4 倍 |
| 登录 | 20 | 37.7 | **42.4** | 38.2 | 持平 | 略低 |

登录的耗时几乎全部在 bcrypt 密码校验上，三者受限于同样的 CPU，结果接近。

延迟中位数（毫秒，越低越好）：

| 接口 | 原版 FPM | 原版 Webman | Gvboard |
|------|------|------|------|
| 节点拉取用户列表 | 691 | 787 | **206** |
| 订阅生成 | 594 | 476 | **136** |
| 用户信息 | 343 | 60 | **33** |
| 节点上报流量 | 297 | 80 | **25** |

**高并发**：300 个并发持续请求订阅（模拟大量客户端同时刷新）：

| | 原版 FPM | 原版 Webman | Gvboard |
|------|------|------|------|
| 每秒请求数 | 84.0 | 111.6 | **358.5** |
| 延迟中位数 | 3.6 秒 | 2.3 秒 | **0.83 秒** |
| 最慢 1% 请求（p99） | 7.0 秒 | 16.4 秒 | **1.3 秒** |

Gvboard 在并发从 50 提高到 300 时吞吐基本不变，延迟按排队线性增长；原版吞吐也不变，但最慢请求的延迟拉长到数秒至十几秒。

**内存占用**（压测期间峰值）：原版 FPM 约 950 MB（Nginx + 40 个 PHP 进程，节点拉取用户列表时每个进程都要加载全部用户），原版 Webman 400～540 MB，Gvboard **80～95 MB**；空闲时 Gvboard 约 35 MB。

#### 100 万用户

100 万注册用户，其中 10 万有效（节点每次拉取 10 万个用户，约 6 MB）。三种服务各自限制为 **4 个 CPU 核心、8 GB 内存**，MySQL 缓冲池（`innodb_buffer_pool_size`）设为 2 GB，节点拉取用户列表的并发降为 5，其它同上：

| 接口 | 原版 FPM | 原版 Webman | Gvboard | 相比 FPM | 相比 Webman |
|------|------|------|------|------|------|
| 节点拉取用户列表（10 万有效用户） | 2.9 | 2.9 | **9.2** | 3.2 倍 | 3.2 倍 |
| 订阅生成（Clash） | 141.0 | 181.3 | **589.9** | 4.2 倍 | 3.3 倍 |
| 用户信息 | 395.0 | 2488.9 | **4873.0** | 12.3 倍 | 2.0 倍 |
| 节点上报流量 | 222.3 | 969.2 | **1977.9** | 8.9 倍 | 2.0 倍 |
| 登录 | 73.1 | **84.0** | 74.5 | 持平 | 略低 |

- 节点拉取用户列表的 p99：原版 FPM 3.1 秒、Webman 3.2 秒，Gvboard **0.63 秒**。
- 内存峰值：原版 FPM 约 **6.2 GB**（每个 PHP 进程都要把 10 万个用户载入内存），原版 Webman 约 1.8 GB，Gvboard 约 **300 MB**。
- `gvboard migrate` 迁移 100 万用户（为每个用户建立主订阅）用时 72 秒。
- 用户量大时请按数据量调大 MySQL 缓冲池。默认的 128 MB 装不下百万用户的表，节点拉取用户的查询两边都要 1～2 秒，差距不明显。

#### PostgreSQL

同一份数据用 `gvboard db-convert` 转到 PostgreSQL 16（35 张表、14 万行，用时 5 秒），1 万用户、其它条件同上：

| 接口 | Gvboard + MySQL | Gvboard + PostgreSQL |
|------|------|------|
| 节点拉取用户列表 | 95.9 | 94.5 |
| 订阅生成 | 359.6 | 406.7 |
| 用户信息 | 2942.1 | 3495.8 |
| 节点上报流量 | 1908.4 | 2014.9 |
| 登录 | 38.2 | 38.5 |
| 300 并发订阅 | 358.5 | 384.8 |

两者相当，PostgreSQL 略快。

#### 队列：流量上报后的处理

节点上报 2000 次流量（每次 100 个用户），之后启动队列把积压的任务全部处理完：

| | 原版（Horizon） | Gvboard（内置队列） |
|------|------|------|
| 灌入时接收上报的速度（20 并发） | 181 次/秒（FPM） | 1805 次/秒 |
| 产生的任务 | 6000 个（每次上报 3 个） | 2000 个 |
| 全部处理完 | 124.7 秒 | **36.8 秒** |
| 内存峰值 | 421 MB（12 个工作进程） | **41 MB** |
| 失败任务 | 0 | 0 |
| 流量写入用户表（`traffic:update` / `traffic_update`） | 2.11 秒 | 0.66 秒 |

两边处理完后，流量统计与用户已用流量的总和都与上报的数据一致。

#### 说明

- 上面的单接口测试只比较请求处理，双方都没有运行队列与定时任务；队列测试与下面的长时间测试运行了全部组件。Gvboard 按默认设置开启了订阅请求日志，原版没有这项功能。
- 原版 Webman 按 `/proc/cpuinfo` 决定进程数，容器内看到宿主机全部核心，开了 24 个进程（真实 2 核服务器上是 4 个），对原版略有利。
- 原版 Horizon 的最大进程数按“内存 GB × 6”计算，容器内看到的是宿主机内存，按此会开到 96 个进程。测试按 2 GB 内存设为 12 个，与真实 2 GB 服务器一致；Horizon 与定时任务进程关闭了命令行 opcache（PHP 默认如此）。
- 数据库与 Redis 和被测服务在同一台机器上，没有网络延迟；实际服务器上数据库查询越慢，双方差距越小。结果用于相对比较，不代表某台服务器的绝对性能。

### 稳定性

**长时间运行**：三者各自运行全部组件（原版：FPM 或 Webman + Horizon + 定时任务；Gvboard：一个进程），以固定速率持续请求 30 分钟：用户信息 24 次/秒、订阅 10 次/秒、节点上报 4 次/秒、节点拉取 1 次/秒。每 5 分钟记录一次：

| | 原版 FPM | 原版 Webman | Gvboard |
|------|------|------|------|
| 内存（全部组件合计） | 570～620 MB，平稳 | 660 → 900 MB，30 分钟内持续上涨 | **48～51 MB**，平稳 |
| 用户信息 p95 | 216～398 ms | 19～43 ms | **3 ms** |
| 节点拉取 p95 | 757～1161 ms | 461～705 ms | **31～35 ms** |
| 未能按时发出的请求 | 每 5 分钟 3～7 个 | 0 | 0 |
| 失败请求、失败任务、内存超限被杀 | 0 | 0 | 0 |

**测试中发现并已修复的问题**：

- 流量统计任务并发写入时，MySQL 会出现死锁，导致少量统计任务失败。现在统计事务通过数据库命名锁依次执行，遇到死锁或锁等待超时会自动重做，上面的队列测试为 0 失败。
- 100 万订阅时，节点拉取用户列表需要 8.7 秒：所有订阅都在同一个权限组，MySQL 选了权限组索引，逐行回表。现在改为 `(权限组, 到期时间)` 联合索引，并单独排除被封禁的用户，同样数据下降到约 0.4 秒，1 万用户时也快了约 8%。执行 `gvboard migrate` 会自动更新索引。

**架构**：

- **部件更少**：原版需要 PHP-FPM（或 Webman）、Horizon、cron 同时正常工作，cron 没配好时定时任务会静默不执行；Gvboard 一个进程包含全部功能，定时任务可在管理端查看与手动执行。
- **需要进程守护**：Gvboard 是单个进程，严重错误或内存超限（如 JS 插件占用过多内存）会导致整个服务重启，必须配置进程守护（systemd、宝塔进程守护管理器或 Docker 的自动重启），部署文档中已包含。原版每个 FPM 请求互相隔离，单个请求出错不影响其它请求。

## 快速安装

Linux 服务器（root 用户）使用安装脚本，支持全新安装、从原 v2board 迁移、升级：

```bash
mkdir -p /root/gvboard-install && cd /root/gvboard-install
curl -fsSLO https://github.com/gunzi-666/gvboard/releases/latest/download/install.sh
bash install.sh
```

国内服务器下载慢时可加速：`GITHUB_PROXY=https://ghfast.top/ bash install.sh`。

需要事先准备好空数据库（MySQL 字符集 `utf8mb4`）与 Redis 6.0+。Docker、宝塔面板、手动安装、从原生产库迁移的步骤见 [部署文档](docs/部署文档.md)。

## 对接节点

节点通信接口（`/api/v1/server/...`、`/api/v2/server/...`）与原版路径相同且始终可用，**不需要开启任何 `compat.*` 兼容开关**。v2node、V2bX 等节点后端按原来的方式填写：面板地址填面板域名，`ApiKey` 填管理端“系统配置 → 节点”中的通讯密钥，`NodeID` 填节点 ID。从原 v2board 迁移的站点，节点配置无需修改。

已在本地用 v2node v0.4.7 实测 VLESS（TCP / REALITY + Vision）、VMess WS、Shadowsocks、Trojan、Hysteria2、TUIC、AnyTLS：节点拉取配置与用户、真实代理流量、流量上报入账、在线 IP 上报均正常。

> v2node v0.4.7 官方镜像的 Shadowsocks 2022 节点会启动失败（`proxy/shadowsocks_2022: bad key`），并导致同一个 v2node 进程里的其它节点也无法启动。这是 v2node 生成内部占位用户密钥的问题，对接原版 v2board 同样存在；上游已在提交 `1a3f896` 修复，请使用之后发布的版本或自行从源码编译。

## 从源码编译

需要 Go 1.26、Node.js 20+（只有修改前端时需要）。

```bash
# 前端（可选，仓库中已包含编译好的页面）
cd web
npm ci
npm run build
cd ..

# 后端
go build -trimpath -ldflags "-s -w" -o gvboard ./cmd/gvboard

# 生成配置、建表、创建管理员、启动
./gvboard init
./gvboard migrate
./gvboard create-admin admin@example.com
./gvboard serve
```

常用命令见 `gvboard --help` 与部署文档的“命令行速查”。
