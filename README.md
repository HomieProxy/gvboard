# Gvboard

Gvboard 是用 Go 重写的代理服务面板，功能与原 v2board（wyx2685 分支）对齐，可以直接接入原项目的生产数据库继续使用。

- 单个可执行文件：用户端、管理端页面已编译在程序中，不需要 PHP 与 Web 根目录
- 数据库支持 MySQL 5.7+ / 8.0 与 PostgreSQL 13+，提供 MySQL → PostgreSQL 转换命令
- 兼容原项目：数据库、节点通信接口、订阅格式、支付回调；迁移后老订阅链接可继续使用

## 主要功能

- **单账号多订阅**：一个账号可购买多个套餐，每个订阅独立的流量、到期时间、订阅链接
- **订阅风控**：按 User-Agent、IP、请求头等规则拦截或记录订阅请求，频率限制、防分享，请求日志与按订阅统计
- **插件**：内置插件（Go，编译进程序）与 JS 插件（沙箱运行，需声明权限与可访问的域名），可监听订单、工单等事件
- **主题**：内置主题，支持安装外部主题
- **部署方式**：前后端不分离（一个程序提供全部页面）或分离部署（前端单独放在 CDN / 静态站点）
- **通知**：多个 SMTP 服务器（故障转移 / 轮询）、管理端可编辑的邮件模板；Telegram 机器人，管理员通知可发到话题群组（订单、工单、告警、每日统计）
- **管理端**：订单补单、订阅管理、节点与权限组、优惠券、礼品卡、公告、工单、知识库、队列监控、系统日志

## 与原版对比

### 功能与架构

| 项目 | 原版 v2board（wyx2685） | Gvboard |
|------|------|------|
| 运行环境 | PHP + Laravel 8，需 Nginx + PHP-FPM（或 Webman）、Horizon 队列进程、cron 定时任务 | 单个可执行文件，队列与定时任务内置 |
| 数据库 | MySQL | MySQL / PostgreSQL |
| 订阅 | 一个账号一个订阅 | 一个账号多个订阅，各自独立流量与到期 |
| 订阅防护 | 一次性 / 限时订阅链接 | 同样支持；另有规则拦截（UA、IP、请求头）、频率限制、防分享、请求日志与统计 |
| 插件 | 无 | Go 内置插件、JS 插件 |
| 部署方式 | 前端随程序部署 | 不分离（页面编译在程序中）或分离部署（提供前端单独部署的配置） |
| 邮件 | 单个 SMTP，模板需改文件 | 多个 SMTP（故障转移 / 轮询），模板在管理端编辑 |
| Telegram 管理员通知 | 私聊管理员 | 可发到话题群组，按订单 / 工单 / 告警 / 每日统计分话题 |
| 已取消订单收到付款回调 | 不处理，也不通知 | 不处理，通知管理员；管理端可补单 |
| 数据迁移 | — | 直接接入原生产库，`gvboard migrate` 升级结构，老订阅链接可继续使用 |

### 性能实测

测试环境：同一台机器，三种服务各自限制为 **2 个 CPU 核心、2 GB 内存**，连接同一个 MySQL 8.0 与 Redis 7；数据为 1 万个有效用户、30 个节点；压测工具 k6 运行在其它核心上。原版使用 PHP 8.2（开启 opcache 与 JIT），FPM 模式为 Nginx + 40 个固定进程，Webman 模式使用原版自带的 `webman.php` 启动。Gvboard 的数据库由同一份原版数据经 `gvboard migrate` 迁移而来。两边返回的内容一致（响应大小相差不到 1%）。

每秒请求数（越高越好），每个接口持续压测 30 秒，全部请求均成功：

| 接口 | 并发 | 原版 FPM | 原版 Webman | Gvboard | 相比 FPM | 相比 Webman |
|------|------|------|------|------|------|------|
| 节点拉取用户列表（1 万用户） | 20 | 25.9 | 24.2 | **89.7** | 3.5 倍 | 3.7 倍 |
| 订阅生成（Clash） | 50 | 81.0 | 111.5 | **367.3** | 4.5 倍 | 3.3 倍 |
| 用户信息 | 100 | 262.5 | 1510.0 | **3033.0** | 11.6 倍 | 2.0 倍 |
| 节点上报流量（每次 100 个用户） | 50 | 159.1 | 571.1 | **1953.0** | 12.3 倍 | 3.4 倍 |
| 登录 | 20 | 37.3 | **42.1** | 38.3 | 持平 | 略低 |

登录的耗时几乎全部在 bcrypt 密码校验上，三者受限于同样的 CPU，结果接近。

延迟中位数（毫秒，越低越好）：

| 接口 | 原版 FPM | 原版 Webman | Gvboard |
|------|------|------|------|
| 节点拉取用户列表 | 756 | 674 | **219** |
| 订阅生成 | 610 | 348 | **135** |
| 用户信息 | 361 | 57 | **32** |
| 节点上报流量 | 293 | 81 | **25** |

**高并发**：300 个并发持续请求订阅（模拟大量客户端同时刷新）：

| | 原版 FPM | 原版 Webman | Gvboard |
|------|------|------|------|
| 每秒请求数 | 77.4 | 112.9 | **357.5** |
| 延迟中位数 | 3.9 秒 | 2.4 秒 | **0.83 秒** |
| 最慢 1% 请求（p99） | 7.2 秒 | 16.5 秒 | **1.4 秒** |

Gvboard 在并发从 50 提高到 300 时吞吐基本不变，延迟按排队线性增长；原版吞吐不变，但最慢请求的延迟拉长到数秒至十几秒。

**内存占用**（压测期间峰值）：原版 FPM 约 950 MB（Nginx + 40 个 PHP 进程，节点拉取用户列表时每个进程都要加载全部用户），原版 Webman 约 450 MB，Gvboard 约 **90 MB**；空闲时 Gvboard 约 35 MB。

说明：

- 测试只比较请求处理，双方都没有运行队列与定时任务（原版的 Horizon、Gvboard 的内置队列）。Gvboard 按默认设置开启了订阅请求日志，原版没有这项功能。
- 原版 Webman 按 `/proc/cpuinfo` 决定进程数，容器内看到宿主机全部核心，开了 24 个进程（真实 2 核服务器上是 4 个），对原版略有利。
- 数据库与 Redis 和被测服务在同一台机器上，没有网络延迟；实际服务器上数据库查询越慢，双方差距越小。结果用于相对比较，不代表某台服务器的绝对性能。

### 稳定性

- **部件更少**：原版需要 PHP-FPM（或 Webman）、Horizon、cron 同时正常工作，cron 没配好时定时任务会静默不执行；Gvboard 一个进程包含全部功能，定时任务可在管理端查看与手动执行。
- **需要进程守护**：Gvboard 是单个进程，严重错误或内存超限（如 JS 插件占用过多内存）会导致整个服务重启，必须配置进程守护（systemd、宝塔进程守护管理器或 Docker 的自动重启），部署文档中已包含。原版每个 FPM 请求互相隔离，单个请求出错不影响其它请求。

## 快速安装

Linux 服务器（root 用户）使用安装脚本，支持全新安装、从原 v2board 迁移、升级：

```bash
mkdir -p /root/gvboard-install && cd /root/gvboard-install
curl -fsSLO https://github.com/gunzi-666/gvboard/releases/latest/download/install.sh
bash install.sh
```

国内服务器下载慢时可加速：`GITHUB_PROXY=https://ghfast.top/ bash install.sh`。

需要事先准备好空数据库（MySQL 字符集 `utf8mb4`）与 Redis 6.0+。Docker、宝塔面板、手动安装、从原生产库迁移的步骤见 [部署文档](docs/部署文档.md)。

## 从源码编译

需要 Go 1.26、Node.js 20+（只有修改前端时需要）。

```bash
# 前端（可选，仓库中已包含编译好的页面）
cd web
npm ci
npm run build
cd ..

# 后端
go build -trimpath -ldflags "-s -w" -o gvboard ./cmd/gvboard

# 生成配置、建表、创建管理员、启动
./gvboard init
./gvboard migrate
./gvboard create-admin admin@example.com
./gvboard serve
```

常用命令见 `gvboard --help` 与部署文档的“命令行速查”。
